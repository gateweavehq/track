# Add or change a sync mutation

A mutation lives in three places that must agree: the wire schema, the server handler that
decides, and the client prediction that makes the UI instant. Work through the steps in order.

## 1. Protocol: `packages/protocol/src/mutations.ts`

- Add a member to the `mutationSchema` discriminated union, named `<entity>.<verb>`.
- Reuse the field schemas at the top of the file (`id`, `title`, `sortOrder`, …). Ids are
  generated by the client (UUIDv7, `uuidv7()` from `@tangent/sync-client`).
- Defaults (`.default(...)`) are applied before the mutation is stored, so client and server see
  the same values.
- Update payloads take a `patch` that is `.partial().refine(nonEmpty)`. Updates to issues also
  carry `baseVersion` for field-level concurrency.
- If you change an entity's shape in `domain.ts`, bump `PROTOCOL_VERSION` in `messages.ts`.
- A new entity touches more places. Bump `PROTOCOL_VERSION` and update:
  - `Entities` and `ENTITY_NAMES` in `domain.ts`, and `Snapshot` in `messages.ts`;
  - a table in the Durable Object (see `schema-change`), its row mapper and `readSnapshot` in
    `packages/sync-server/src/state.ts`;
  - `Tables`, `SyncState` and `Replica.reset`/`snapshot` in `packages/sync-client/src/store.ts`,
    and `MemoryPersistence` in `persistence.ts`. The IndexedDB stores in `idb.ts` follow
    `ENTITY_NAMES` on their own.

## 2. Server: `packages/sync-server/src/mutations.ts`

- Add a `case` to the `switch` in `applyMutation` and a handler function next to the others.
- Check permissions first (`requireAdmin(actor)` for admin-only writes).
- Reject with `throw new MutationRejected(reason, message)`: `invalid`, `forbidden`, `not_found`
  or `conflict`. Throwing rolls back every write the mutation made.
- Write through Drizzle's sync API (`.get()`, `.all()`, `.run()`, `.returning().get()`). No
  `await`: the handler runs inside `transactionSync`.
- Record every visible change with `changes.put(entity, row)` or `changes.delete(entity, id)`.
  Rows that carry a `version` get `changes.nextVersion`.
- For fields edited concurrently, follow `updateIssue`: stamp each written field with
  `{ version, clientId }` and skip fields another client wrote after `baseVersion`.

## 3. Client prediction: `packages/sync-client/src/optimistic.ts`

- Add a `case` that applies the mutation to the `Draft`.
- It must be safe to apply to state that already contains its effect, because it is replayed
  after the server's delta arrives and before the ack. Creates skip ids that already exist.
- Skip anything the server would reject rather than guessing. The rejection arrives on its own.
- Server-assigned values (numbers, timestamps) are predicted plausibly; the server's row replaces
  them.

## 4. Tests

- `packages/sync-server/test/sync.test.ts`: the happy path, every rejection reason the handler
  can produce, permissions, and what other clients receive.
- `packages/sync-client/test/store.test.ts`: the prediction, including replay over a state that
  already has the server's result.
- `packages/sync-client/test/client.test.ts`: only if the mutation adds client behavior beyond
  prediction, such as a new conflict case.

## 5. Docs and UI

- Update `docs/architecture.md` if the mutation changes sync semantics or concurrency rules.
- In the UI, call `client.mutate({ name, args })`. Don't await it for rendering; the change is
  already visible. Rejections reach the client's `onReject`.

## 6. Verify

```sh
pnpm --filter @tangent/sync-server test
pnpm --filter @tangent/sync-client test
pnpm verify
```
